## 一、结论摘要

**待机耗电的真正原因是"设备根本睡不下去"：每 0.46 秒尝试一次 s2idle，0.1–0.4 秒就被唤醒，AP 有一半以上时间醒着。**

- 纯息屏 IDLE 窗口实测 **97–122 mA = 1.66–2.07 %/h**，8 小时约 13–17%，与"一晚十几个点"吻合。
- 唤醒源（50 秒差分）：**`[timerfd]` 2.13 次/秒 + `qcom_rx_wakelock` 0.50 次/秒 = 2.73 次/秒**。
- 代价：`android.system.suspend-service` 每 15 分钟烧 127–186 秒 CPU（16–21% 单核），
  UID 1000 合计 230–294 秒，UID 0 内核 92–130 秒。

**这不是应用层问题**，也不是京东/NoActive 的问题，而是固件/驱动层的周期性唤醒。

## 三、机制：460 ms 的唤醒链

ftrace `power/wakeup_source_activate`（息屏 Dozing，4 秒采样）：

```
+0.000  kworker/3:0        -> [timerfd]
+0.050  dp_rx_thread_0     -> qcom_rx_wakelock      Wi-Fi 收包
+0.058  tee-supplicant x2  -> gh_vcpu_ws            TEE
+0.075  AlarmManager-4714  -> eventpoll + [timerfd] system_server
+0.101  trustedvm_vcpu0/1  -> gh_vcpu_ws            Gunyah 可信虚拟机
（约 460 ms 后重复）
```

关键佐证：
- 同一个 tracepoint 在**亮屏时几乎不出现**（`[timerfd]` 0.07 次/秒）→ 这条链只在"正在尝试挂起"时存在，
  是挂起-重试循环自身，不是某个 App 的定时器。
- `[timerfd]` 是旧内核的误标：内核提交 *fs: Improve eventpoll logging to stop indicting timerfd*
  明确写了 timerfd 不建 wakelock，实际是 **eventpoll 的 EPOLLWAKEUP 锁**按 fd 名字命名。
- 小米社区另一台 HyperOS 设备（Redmi Note 13 Pro）的技术报告里出现逐字相同的
  `Abort: Pending Wakeup Sources: [timerfd] → PM: suspend exit → PM: suspend entry (s2idle)`。

设备端 5 分钟挂起统计（23:42–23:47）：239 次尝试 / 301 秒（0.79 次/秒），失败 38 次，
timerfd abort 199 次，WLAN PCIe `-11` 5 次。
内核 `/sys/power/suspend_stats` 累计：success 4680 / fail 997（failed_freeze 589、failed_suspend 385），
last_failed_dev = `0000:01:00.0`（cnss WLAN），errno `-16`/`-11`。

## 四、证据分级

### 已证实
1. 息屏无法维持挂起：每 0.46 s 一次尝试、0.1–0.4 s 被中止，awake 占 52.5%–62.5%。
2. 待机功耗 1.66–2.07 %/h（97–122 mA），与外推 8 小时 13–17% 一致。
3. 唤醒源以 `[timerfd]`/eventpoll（2.13/s）与 `qcom_rx_wakelock`（0.50/s）为主。
4. `suspend-service` 是最大单一 CPU 消耗者（16–21% 单核），但它是"重试循环"的结果而非原因。
5. **应用层不是原因**（反证见下）。

### 候选（有证据未闭环）
- TEE（`tee-supplicant`）/ TrustedVM（`trustedvm_vcpu0/1`、`gh_vcpu_ws`）与 timerfd 同相位调度，
  疑为厂商固件周期任务；只读条件下无法再归因。
- WLAN 驱动挂起失败 `-11/-16`（15 分钟 5–25 次），占比不高但是持续的失败来源。
- mDNS/SSDP 组播：临时屏蔽 5353/1900 后 `qcom_rx_wakelock` 0.73→0.18 次/秒（−75%），
  但总唤醒率不变（`[timerfd]` 接棒 0.73/s）。

### 已排除（有反证）
| 假设 | 反证 |
|---|---|
| 某 App 的唤醒锁 | QQ 后台锁 13.9 s 的窗口与 282 s 的窗口耗电都是 101/105 mA；`/sys/power/wake_lock` 为空 |
| 京东 | 息屏窗口 CPU 0.000 s、Wi-Fi 0 包、无唤醒锁 |
| NoActive / NoActive Monitor | 无 CPU、无 partial wakelock 计数行 |
| 息屏显示（AOD） | `doze_always_on=0` |
| 后台扫描 | `wifi_scan_always=0`、`wifi_wakeup=0` |
| 我自己的 ADB 诊断 | adbd 2.2–6.8 s CPU/15 min（<1%）；19:10 窗口曾拉 2.1 MB dmesg（TX 19.5 MiB）已作废，之后 TX 降到 ~2 MiB，耗电率不变 |
| 用户"不开 ADB 也费电" | 与实测一致，ADB 只占 0.5% |

| 优先级 | 动作 | 预期 | 撤销方式 |
