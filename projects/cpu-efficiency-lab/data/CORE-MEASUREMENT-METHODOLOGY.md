# 单核功耗测量：方法学与实测否证

设备：`2410DPN6CC`（SM8750）/ Android 16 / KernelSU  
日期：2026-11-11

本文记录「如何把单颗 CPU 核心的功耗从整机功耗里分离出来」这条路上的
所有尝试与实测结果。**核心结论：在这台设备上做不到，已用数据否证。**

保留这份记录的目的：避免下次再从同一个坑开始。

---

## 为什么必须做基线减除

`current_now × voltage_now` 测的是**电池侧总放电**，包含屏幕、内存、
射频、基带、传感器。实测：

| 场景 | 整机功率 |
|---|---|
| 屏幕最低亮度、系统空闲 | ~1.0 W |
| 单核最高频满载 | ~1.93 W |

即使按最乐观的估计，非 CPU 部分也占 **54%**；在低频端（556 MHz）
CPU 真实贡献只有约 0.08 W，基线占 **93%**。

**所以「低频 nJ/op 更高」这类结论如果没扣基线，是不可信的**——
分母被灌入了约 1 W 的固定开销，低频段被系统性高估。

## 尝试 1：current_now 瞬时采样 → 否证

同一静止系统（什么都没做）连续 6 个 4 秒窗口：

```
余电读数：97mA 105mA 115mA 199mA 225mA 378mA
折算功率：0.41W 0.44W 0.48W 0.84W 0.95W 1.59W
```

- 均值 0.79 W，标准差 0.46 W，**相对 58%**
- 极差 **1.19 W**

而单核满载相对空闲的真实增量只有 **0.1–0.5 W**。

**噪声是信号的 2–10 倍，减除无意义。**

## 尝试 2：满载减空闲（current_now 口径）→ 否证

用 `core_measure.sh` 跑了 45 行（每核每频点一对 load/idle，
`taskset` 把对照组钉在同一核上以保持固定开销一致）。

结果：**22% 的行出现 `load < idle`，算出的 cpu 功耗为负值**（最低 −0.52 W）。

这不是实现 bug（`setsid` 的 wait 缺陷已修），而是上面那个噪声问题的必然结果。

## 尝试 3：库仑计 charge_counter → 量化受限

`charge_counter` 是 PMIC 维护的累积库仑积分，天然把高频抖动平均掉。
实测信号清晰：

| 场景 | 65s 内下降 |
|---|---|
| 空闲 | 2000 单位 |
| 单核满载 | 8000 单位（约 4 倍） |

**但分辨率只有 1000 单位**（0.001 Ah），60 秒窗下单核增量只产生
约 6420 单位，量化误差占 **15.6%**。

要压到 5% 以内需要 **≥180 秒**窗口：

| 窗口 | 总耗电 | 单核增量 | 量化误差 |
|---|---|---|---|
| 60s | 1,860 | 6,420 | 15.6% |
| 120s | 3,720 | 12,840 | 7.8% |
| 180s | 5,580 | 19,260 | **5.2%** |
| 300s | 9,300 | 32,100 | 3.1% |

180 秒窗意味着 **6 分钟/测点**（load + idle 各 180s）：

```
8核 × 3频点 = 24 点 → 144 分钟
8核 × 4频点 = 32 点 → 192 分钟
```

## 环境干扰：比测量方法本身更致命

测量期间反复出现 bench 吞吐崩塌（同一频点 126 Mop/s → 3.9 Mop/s），
排查结果是**内存压力**，不是 CPU 本身：

```
MemAvailable: 364 MB / 15113 MB
SwapFree:    3884 MB（已用 3.9 GB）
Top PSS: 微信 457M  钉钉 712M  QQ 532M  B站 416M  system 643M
```

内存吃紧时 bench 被反复换页，`elapsed` 从精确的 3.000s 涨到 4.53s，
吞吐掉 10 倍。

清空后台后恢复：

```
MemAvailable: 8235 MB
QC ops: 193.0M / 192.8M / 192.1M   （波动 0.5%）
```

**教训：任何 CPU 测量前必须做环境准入检查**，判据是同一配置下
连续 3 次 bench 的 `ops` 相互差异 <5%，且 `elapsed` 与请求值偏差 <0.1s。
不达标就该等，而不是硬测。

## 反向验证：设备本身能被可靠测量

为了确认问题出在「功率」而不是「吞吐」，单独验证吞吐：

```
同核同频（core0 @ 1785.6MHz）连续 6 次：
el=3.000015 ops=112.7M
el=3.000016 ops=119.5M
el=3.000018 ops=122.8M
el=3.000031 ops=124.2M
el=3.000010 ops=118.6M
el=3.000019 ops=109.4M
```

`elapsed` 全部精确 3.000s，ops 标准差约 5%。

**结论：吞吐可信，功率不可信。** 所以：
- **重复次数**：每点 3–5 次足够（3 次已能把均值误差压到 3% 内）
- 主要误差源是设备状态漂移，不是随机噪声，所以增加次数收益递减

## 当前可用的替代口径

既然绝对功耗测不准，改用**等吞吐对比**——不比较绝对 nJ/op，
只比较「完成同样的工作量，谁的整机功率更低」。这个口径不受
固定开销影响（因为它对所有测点都是同一份偏移）。

低包络口径下（噪声只抬高读数，故 min 更接近真值）：

| 大核群 | 小核群达同吞吐 | 小核省 |
|---:|---:|---:|
| 71.4 Mop/s @ 1.393 W | 66.6 Mop/s @ 0.986 W | 29.2% |
| 98.6 Mop/s @ 1.410 W | 95.3 Mop/s @ 1.081 W | 23.3% |
| 173.1 Mop/s @ 1.654 W | 169.2 Mop/s @ 1.387 W | 16.1% |
| 218.1 Mop/s @ 1.907 W | 193.7 Mop/s @ 1.587 W | 16.8% |

10 个可比点里 9 个小核更省，区间 16–29%。唯一例外（−0.8%）落在噪声内。

**这个结论是稳的**，因为它只依赖功率的**相对**大小，而同一批测量里
固定开销相同。

## 若要真正做成

需要绕开电池电流计，改用：

1. **外接功率计**（USB 电流表 / 专业功耗分析仪）——最直接，但需要硬件
2. **PMIC 内部计数器**——本机的 `charge_counter` 分辨率不够，更高端的
   平台有 `energy_now`（本机不存在）
3. **热学方法**——用已知热阻从温升反推功耗，但时间常数太长
4. **间接法**——只测等吞吐下的相对差异（本文档采用的方法）
