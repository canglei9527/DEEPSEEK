# Power Lens 自然调频观察审计

日期：2026-11-13
范围：对本地 Power Lens 2.5 APK/模块的静态分析，以及设备上已有采集日志的只读核验。未启动、停止或修改 Power Lens、采集器、应用和设备设置。

## 结论

Power Lens 可以提供一份有价值的**自然 DVFS 观察时间序列**：root 侧采集器把 CPU policy 当前频率、整机电池 `charge_counter` 和 UID 累计 CPU 时间写入同一 TSV，记录使用共同的 epoch 毫秒时间戳。它适合回答“设备在自然运行中访问过哪些 policy 状态、频率状态如何随时间变化”这类问题。

它不能单独生成可信的 CPU 频率—能效曲线，也不能证明某个频率组合是最优。频率是约一分钟一次的 policy 端点快照；电池计数是整机电池侧累计量；日志没有可配对的实验工作量/吞吐结果、CPU/SoC 电源轨能量或固定频率控制。把一个采样端点的电池增量全部归给该端点频率，会产生时间归属错误。

## 已核验的数据链

- 采集器读取 policy 的 `scaling_cur_freq`、上下限、`related_cpus`、在线掩码和核心数，同时读取电池 `charge_counter`、容量/状态及 UID CPU 累计计数。
- CPU 记录格式为：`epoch_ms / cpu policy / policy_name / current_kHz / min_kHz / max_kHz / related_cpus / online_mask / core_count`。
- 本设备的两组 policy 分别覆盖 CPU 0–5 与 CPU 6–7；这是 policy/簇级频率，不是八个独立核心的频率读数。
- Power Lens Activity 会在所选时间窗内从同一日志取最新的 policy 快照显示；原始 TSV 仍保留较早记录，可以离线重建采样历史。
- UID CPU 字段是累计 CPU 时间，App 通过相邻记录差分；它只能作为活跃度协变量，不是完成的操作数或吞吐量。
- 静态检查未发现采集器读取 `current_now`、`voltage_now` 或 CPU/SoC 电源轨能量计数器。`charge_counter` 应始终标成整机电池侧读数。

## 聚合审计结果

以下数字来自设备日志的本地只读副本；发布版本不包含原始日志、UID、包名、设备标识或精确使用时间戳。

- 共有 3,023 个时间戳组，其中 3,020 个包含电池行。
- 共有 1,066 个时间戳包含 CPU policy 行；其中 1,056 个同时包含两组 policy 和电池行。
- CPU policy 与电池配对样本的中位间隔为 60.32 秒，p90 为 60.413 秒；存在超过 120 秒的缺口，不能假设采样均匀。
- policy0 观察到 13 个当前频率值，policy6 观察到 12 个当前频率值，联合出现过 52 种 policy 频率状态。
- 有 840 个相邻配对区间满足不超过 120 秒且两端均为 `Discharging`。这只是可供探索性整机电量变化分析的候选区间，不是 840 次受控重复实验。
- 日志跨越多天、包含充电/满电状态、不同前后台活动和长时间缺口。任何离线图都必须分段保留充电状态、实际时间差和缺测标记。

## 当前可以绘制的内容

从原始日志离线可以绘制：

- policy0/policy6 当前频率随墙上时间的变化；
- 实际出现过的联合 policy 状态及其出现次数；
- 按实际时间差归一化的整机电池 `charge_counter` 变化；
- UID 累计 CPU 时间增量作为活跃度参考；
- 充电状态、长间隔、缺失 policy、上下限变化和无效区间。

这些图的标题和字段应使用“自然 DVFS 观察”“整机电池侧电量变化”或“policy 状态统计”等表述。不得标为 CPU 功率、CPU 能量/操作、固定频率结果或全局最优。

## 要得到可信能效曲线还需要什么

无锁频条件下仍可以做观察性比较，但必须把以下信息放入同一实验协议：

1. 可重复的工作负载、完成工作量/吞吐和延迟指标。
2. 更短且实际核验过的采样间隔，记录 policy 联合状态的持续时间，而不只记录端点频率。
3. 电池状态、温度、在线核、后台/前台状态、UID CPU 时间和系统限频事件。
4. 足够的重复次数、相近温度与电量条件，并对自然访问到的联合状态做分层比较。
5. 电池电流/电压或外部功率测量（如果设备明确提供），并始终标明这是整机电池侧功率；不能冒充 CPU 电源轨。

最终比较应使用“完成单位的整机电池侧能量”并同时约束吞吐/延迟。若某个联合状态没有足够驻留或没有匹配工作量，不能从该状态的自然出现次数推断最优。

## 与项目现有数据的关系

Power Lens 审计不替换项目已有的 `efficiency-report`、配对空闲基线或 `matrix-sweep` 证据链。历史固定频率 TSV 的问题仍按项目报告处理；Power Lens 日志只能作为独立的自然运行观察来源。它不会解除 `matrix-sweep` 的恢复门禁，也不会授权锁频、改 governor、运行负载或安装模块。

详细 APK/DEX/模块静态材料和原始设备日志仅保留在本机取证目录，因包含设备活动和应用/UID 数据，不纳入公开版本库。
